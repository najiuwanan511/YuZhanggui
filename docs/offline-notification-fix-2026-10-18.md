# 掉线通知漏发修复（2.3.24）

用户运行 2.3.23，通知渠道已勾选账号异常/掉线和凭证更新，账号页面显示“连接断开”和“需要验证”，但没有推送。

## 源码确认的原因

1. `WebSocketServiceImpl.triggerWsDisconnectNotify` 在入口检查邮件掉线通知开关，关闭邮件通知就提前返回，连带跳过 PushPlus、Bark、Webhook 等渠道。
2. 掉线通知仅在三次重连返回失败时触发。异常关闭本身不通知，重连抛异常时也漏过该分支；应用重启后已经离线或待验证的账号不一定再发生关闭回调。
3. 待验证通知用“本次是否从正常状态变为 -2”判定首次事件。重启后数据库已是 -2 且平台没有返回新验证链接时，首次事件可能被漏掉；异步通知提交失败也被提前记为已通知。
4. Cookie 过期通知先调用邮件，邮件任务提交失败或没有邮件服务时，多渠道通知无法执行。

这些是源码确认的漏触发路径。未连接用户 fnOS 数据库或 PushPlus 服务，不能据此确认每次历史漏发的具体分支或实际 Token 是否可用。

## 修复行为

- 邮件和多渠道各自执行、各自处理异常。PushPlus 仍遵守渠道配置中的“账号异常/掉线通知”，不再受邮件开关控制。
- 当前连接异常关闭立即提交掉线通知，心跳确认超时及多次重连异常也触发；忽略旧连接迟到的回调。
- 每分钟在业务线程检查正常启用或待验证、但未连接的账号，补报没有回调的历史离线状态。维护标记生效和应用关闭期间不告警；禁用账号不告警。账号保持启用时，手动停止后若持续离线也会在定期检查中提示。
- 同一账号十分钟内合并通知提交，恢复连接后开始新的事件。并发回调与轮询只提交一次；所有通知任务均被拒收时释放防抖，下次可重试。通知服务商实际发送失败仍由现有通知服务重试和记录，异步提交成功不等于用户已收到。
- 已是 -2、没有验证 URL 的账号也发送首次验证通知；提交失败不再记为已通知。凭证过期时独立提交多渠道通知。
